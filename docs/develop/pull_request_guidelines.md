# Pull Request 协作指南

## 协作原则

PR 不只是代码的交付，也是提供给 reviewer 的评审材料。PR 作者应主动降低理解改动、验证正确性和识别风险的成本。由 AI 完成的改动同样遵守这一原则。

### 面向人类协作

PR 的开发、评审和讨论包含大量人类参与者。所有参与者在沟通中都应保持友好、尊重和建设性的态度，聚焦问题本身。参与其中的 AI Agent 应在保证准确性的前提下，以人类易于理解为目标，使用自然、专业、清晰且符合工程协作习惯的表达。应优先沿用项目和领域中已有的术语与叙述方式，保持措辞直接、克制，避免引入不必要的陌生概念或自造表达。

### 让改动容易理解

提供理解改动所需的背景，说明要解决的问题和方案的核心思路。不能假设 reviewer 参与过开发过程，也不应让 reviewer 仅凭代码反推改动意图。

### 让改动容易阅读

围绕一个清晰目标组织 PR，并按照适合阅读的顺序组织代码、commit 和说明。应区分重构、行为变化和机械修改，使 reviewer 能快速找到主干，逐步建立对改动的理解。

### 让正确性容易判断

主动说明关键设计选择、系统约束、风险、边界条件和验证证据。指出最需要 reviewer 关注的部分，并如实披露尚未验证或仍不确定的内容。

### 让评审负担保持合理

作者应综合考虑实现完整性、开发效率和 reviewer 的理解成本，选择合适的 PR 边界。对于包含多个相对独立目标的改动，建议拆分；对于可以按依赖关系分层、但无法彼此独立合入的大型改动，建议使用 GitHub stacked PR，使每一层都能单独理解和评审；对于不适合拆分的大型改动，应提供清晰的阅读线索。

## 标题与正文

PR 标题必须使用英文，并遵守 [Commit message 格式](commit_requirements.md#commit-message-格式)：

```text
[component] description
```

PR 描述正文建议同时提供内容一致的中文和英文版本。使用 AI Agent 创建或更新 PR 描述时，必须提供中英文两个版本。采用双语正文时，中文版本在前，英文版本在后，两者使用水平分割线 `---` 分隔，不额外添加用于标识语言的标题。代码、命令和文件路径等无需翻译的内容可以直接复用。

## 发起 PR 前

作者应以 reviewer 的视角完整检查最终 diff，移除无关改动和临时内容，并确认 PR 提供的信息足以支持一次有效评审。

## 参与 Review

Reviewer 应尽量说明意见背后的原因和风险，并帮助作者区分必须解决的问题、改进建议和需要进一步确认的疑问。

使用 AI Agent 生成 review 总结、实质性意见或讨论回复时，使用者仍应检查最终内容的准确性。建议参照 PR 正文格式同时提供中文和英文版本，两者使用水平分割线 `---` 分隔。
