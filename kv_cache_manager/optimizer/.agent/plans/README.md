# Optimizer 计划文档

任何会改变 optimizer 代码、行为、流程或用户可见文档的需求，都必须在实现前先在这里写 plan 或设计文档。

## 与 Tasks 的关系

- `tasks/` 记录用户要什么，以及为什么要做。
- `plans/` 记录准备怎么做，以及如何验证。
- `workflows/` 记录实现完成后的实际执行过程、逐文件改动和测试结果。

每个 task 应链接到一个主要 plan。一个 plan 也应反向链接到对应 task。

## Plan Review 硬约束

plan 写完后必须先和用户讨论设计决策与设计细节，用户确认后才能开始实现。尤其是新增 optimizer 能力、trace/config 语义、命中率口径、调度行为、storage-pool/P2P 行为或分析输出时，不能由 agent 直接把未确认的假设实现成代码。

允许在用户确认前继续做的事：

- 阅读相关代码和文档。
- 补充或修正 plan。
- 列出备选方案和取舍。
- 明确哪些参数需要用户、部署配置或 trace 元数据确认。

用户确认前不允许做的事：

- 修改生产代码。
- 修改测试来固化某个未确认行为。
- 更新用户可见文档使未确认行为看起来已经定稿。
- 用 workflow 替代 plan review。

## 文件命名

使用和 task 相同的短标题：

```text
YYYY-MM-DD-short-title.md
```

## 必填内容

从 [TEMPLATE.md](TEMPLATE.md) 开始。plan 必须包含：

- 当前状态
- 设计或行为方案
- 待用户确认的设计决策
- 用户确认记录
- 预计改动文件 / 模块
- 兼容性和迁移说明
- 校验计划
- 如适用，包含开源 PR 说明

文档类工作可以写轻量 plan，但实现前仍必须有 plan。
